## Method

- Each resume is its own corpus, as in the app's single-user vault.
- Strategies call retrieveVault / semanticRanking / reciprocalRankFusion from lib/, the same code the app runs.
- Limit 8 = DEFAULT_VAULT_LIMIT.
- The app always anchors the summary at rank 1 and keeps at most 3 chunks per role; the metrics include that behaviour.
- Relevance grades 1-3; recall and MRR count grade >= 2; nDCG gain is 2^g - 1. MRR is effectively MRR@8.
- Latency is the median of 3 timed retrieve() calls per query. For embedding strategies one query-embedding timing per query is added to that median, and the same query-embedding timing sample is shared by every embedding strategy for that query; chunk vectors are precomputed as in the app's index.
- The summary chunk is always placed at rank 1, so unless a query labels the summary at a grade >= the relevance threshold, MRR is at most 0.5; IDCG ignores the summary anchor and the 3-per-role cap, so nDCG@k cannot reach 1. Compare strategies with each other, not against 1.0.
- Rerank strategies take the top N of their base ranking before the 3-per-role cap, score (query, passage) pairs with the cross-encoder on CPU in Node, then apply the same summary anchor and 3-per-role cap. That latency is Node CPU; a browser (WASM) will be slower. The top 30 rows are sensitivity rows that the decision rule never adopts.
- Primary metric is ndcg@8: it is graded, covers the full 8-chunk context and is order-sensitive.
