# Roadmap: iLoveEmployment

## Overview

Milestone "AI engineering depth" takes the shipped six-engine, local-first platform and backs every quality claim with a measured number. It starts by measuring retrieval (labelled dataset, CI-gated metrics), uses that harness to decide whether an on-device reranker earns its place, then runs the behavioural evals against real models with cost, citation precision and a calibrated judge. With measurement in place, it adds a bounded "Apply to this job" agent that composes the existing engines, structured profile extraction with skill normalization and resume versions, and finally per-run observability traces surfaced in the "How this was generated" panel.

- [ ] **Phase 3: LLM Evaluation** - Real-model eval runs with model comparison, cost, citation precision, fabrication rate and a calibrated LLM judge
- [ ] **Phase 4: Agent Workflow** - Bounded tool-calling "Apply to this job" workflow with budgets, resumable state and human approval checkpoints

## Phase Details

### Phase 1: Retrieval Evaluation
**Goal**: The quality of vault retrieval is measured on a labelled dataset, published per strategy, and protected against regressions in CI
**Depends on**: Nothing (first phase)
**Requirements**: REVAL-01, REVAL-02, REVAL-03, REVAL-04
**Success Criteria** (what must be TRUE):
  1. The repo contains at least 3 synthetic resumes (different seniorities/domains) and at least 60 queries with graded relevant chunk ids, including paraphrase queries sharing no keywords with their targets
  2. Running one script prints recall@3/5/8, MRR and nDCG@k for keyword (BM25), embeddings-only and hybrid (RRF), using the same `retrieveVault` / `reciprocalRankFusion` code the app ships
  3. `evals/RETRIEVAL.md` is regenerated by that script with per-strategy metrics, a lexical vs paraphrase breakdown and latency per strategy
  4. CI runs the keyword-only metrics without network or API key, and a deliberately degraded BM25 change fails the build against the recorded baseline

### Phase 2: Reranking
**Goal**: A cross-encoder reranker is either adopted with a measured win or rejected with recorded numbers, never shipped on faith
**Depends on**: Phase 1
**Requirements**: RERANK-01, RERANK-02, RERANK-03
**Success Criteria** (what must be TRUE):
  1. An on-device Transformers.js cross-encoder reranks the hybrid top-N candidates, and its model loads only after the user opts in (first-load JS unchanged)
  2. `evals/RETRIEVAL.md` includes a hybrid+rerank row alongside hybrid alone, with the primary metric delta and added latency
  3. The adoption decision (enabled in the app or not) and the numbers behind it are recorded in the repo and in PROJECT.md Key Decisions, and the app's behaviour matches that decision
**Plans**: TBD

### Phase 3: LLM Evaluation
**Goal**: Generation quality is measured against real models, with cost, grounding and judged quality reported side by side
**Depends on**: Phase 2
**Requirements**: LEVAL-01, LEVAL-02, LEVAL-03, LEVAL-04, LEVAL-05, LEVAL-06
**Success Criteria** (what must be TRUE):
  1. The eval case set has at least 25 cases covering all six engines, and a report from a run against at least one real model is committed
  2. One command runs the same cases across multiple models/providers and produces a side-by-side comparison with tokens, latency and estimated cost per case and per model
  3. Each run reports citation precision (cited chunks that truly support the claim) and fabrication rate
  4. An LLM-as-judge scores outputs on a written rubric, and its agreement with a hand-labelled subset is reported as a number
**Plans**: TBD

### Phase 4: Agent Workflow
**Goal**: A user can paste a job description and walk through a bounded, resumable "Apply to this job" workflow that reuses the existing engines and stops for their approval
**Depends on**: Phase 3
**Requirements**: AGENT-01, AGENT-02, AGENT-03, AGENT-04, AGENT-05, AGENT-06
**Success Criteria** (what must be TRUE):
  1. From a job description, the workflow calls fit check, tailor resume, cover letter and outreach message as tools and produces each artifact with the same grounding guarantees (citation scrubbing, invented-figure check) as the standalone tools
  2. The user approves or edits at checkpoints (after fit check, before outreach); a SKIP verdict ends the workflow unless the user explicitly overrides it
  3. Exceeding the step or token budget stops the run with a clear, user-visible reason
  4. Closing the page mid-run and returning lets the user resume from the persisted vault state (steps, tool calls, outputs)
  5. Scripted-model tests cover tool selection, budget stop and approval gating, and at least 3 agent eval cases run in the eval harness
**Plans**: TBD
**UI hint**: yes

### Phase 5: Document Intelligence
**Goal**: Uploading a resume yields a confirmed, structured profile with normalized skills and tracked resume versions, with extraction accuracy measured
**Depends on**: Phase 4
**Requirements**: DOC-01, DOC-02, DOC-03, DOC-04
**Success Criteria** (what must be TRUE):
  1. After uploading a resume, the user sees a typed, validated profile (contact, roles with dates, education, skills, projects) and can confirm or correct each field
  2. Skill aliases (e.g. "JS", "ReactJS") resolve to canonical taxonomy entries, and fit and ATS scoring match on the canonical skill
  3. A script reports field-level precision/recall of profile extraction against labelled resumes, with results committed
  4. The vault lists resume versions (base and tailored) with the job each targeted, and the user can view a diff between versions
**Plans**: TBD
**UI hint**: yes

### Phase 6: Observability
**Goal**: Every run is explainable step by step through a structured trace, exportable without leaking user content
**Depends on**: Phase 5
**Requirements**: OBS-01, OBS-02, OBS-03
**Success Criteria** (what must be TRUE):
  1. Every run (standalone tools and agent workflow) emits a structured trace covering retrieval, context blocks, model calls, review pass and finalizers, with timings and token counts
  2. In development the trace prints to the console; when an OpenTelemetry or Langfuse backend is configured it is exported there, and no user content appears in exported traces unless the user opts in
  3. The "How this was generated" panel shows a per-step timing waterfall built from the run's trace
