# Phase 5 — UI Design Contract

> Visual and interaction contract for Phase 5: Document Intelligence. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Requirements covered by UI: DOC-01 (review and confirm typed profile), DOC-02 (canonical skill names shown), DOC-04 (resume versions list and diff). DOC-03 (accuracy script) has no UI.
> No CONTEXT.md exists and the user was unavailable. Every choice that would have been a question is listed under "Assumptions for the user to confirm" at the end.

---

## Scope and Placement

All Phase 5 UI lives on the existing `/vault` page, inside `components/vault/VaultManager.tsx` (or new sibling components in `components/vault/` that it renders). No new route. The page shell (`tool-hero`, `max-w-[1000px]` content column, `space-y-8` section rhythm) is unchanged.

Three surfaces, in page order:

1. **Resume import (existing section "Add your resume")**: gains an "extracting" state and, on success, hands off to the Profile Review panel.
2. **Profile Review panel (new)**: appears directly under the import section when an extraction result is waiting for confirmation, and is also reachable for the saved profile ("Review profile" button in the existing Profile section once a structured profile exists).
3. **Resume versions (new section "Resume versions")**: placed between "Semantic search" and "Add a story, win or note". Contains the list and the diff view.

The `ResumeField` in `components/engine/PresetRunner.tsx` (tool pages) is NOT changed in this phase. Its paste/upload and "Save to vault" flow stays as is. A one-line pointer is added to its help text only if the planner finds it trivial: "Review the structured profile in your Career Vault." (optional, see Assumption 9).

Phase 4 dependency: tailored-resume version entries are created by the agent workflow. This phase only reads them. Any entry that exists in the version store appears in the list with no further UI work.

## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Gap between a field's label and its badge; icon-to-text gap inside badges |
| sm | 8px | Gap between badges; gap between action buttons; row inner vertical gaps |
| md | 16px | Field grid gap (`gap-4`); list row padding; between a field and its help text group |
| lg | 24px | Padding inside repeating cards on desktop; gap between profile groups (Contact, Roles, Education...) |
| xl | 32px | Gap between top-level vault sections (existing `space-y-8`) |
| 2xl | 48px | Not used in this phase |
| 3xl | 64px | Not used in this phase |

Exceptions:
- Existing sections use `p-5` (20px). New sections copy that for visual parity with siblings. This is the only non-multiple-of-4 value and is inherited, not introduced.
- Touch targets: every button, select, checkbox, and row action is at least 44px tall (`field-control` is already `min-height: 44px`; `cta-*` are 48px). Compact text buttons ("Edit", "Remove", "Confirm") that render as 13px text get `min-height: 44px; min-width: 44px` via padding, not via visible size.
- Skill chips inside the review panel are 32px tall visually but carry a 44px hit area (vertical padding on the button wrapper).

## Typography

Exactly four sizes and two weights for all new UI. Existing page-level headings (page `h1`) are untouched.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (field values, list row text, diff lines) | 15px | 400 | 1.5 |
| Label (field labels, badges, meta text, help text, buttons inside rows) | 13px | 600 | 1.4 |
| Heading (panel/section titles such as "Review your profile", "Resume versions", group titles) | 20px | 600 | 1.2 |
| Display | not used in this phase | n/a | n/a |

Notes:
- Help text, timestamps and secondary metadata use the Label size (13px) at weight 400, line-height 1.4. This is the only place the Label size uses weight 400; all other Label text is 600. New help text overrides the existing `field-help` size (12.5px) to 13px.
- Existing section titles in VaultManager are `text-[15px] font-bold`. New section titles use the Heading role (20/600) to give the review panel and versions section clear hierarchy; do not retrofit old sections in this phase.
- Do not use weights 500, 650, 700, 800 in new code.

## Color

Project tokens from `app/globals.css`: `--paper #ffffff`, `--mist #f3f4f7`, `--ink #15171c`, `--slate #5e6472`, `--faint #8c919c`, `--rule #e4e6eb`, `--red #e5322d`, `--red-deep #c4241f`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--paper`) | Page and panel backgrounds, field inputs |
| Secondary (30%) | `#f3f4f7` (`--mist`) with `#e4e6eb` (`--rule`) borders | Panel header strips, version rows on hover, unchanged diff context lines, disabled fields, skill chips (neutral) |
| Accent (10%) | `#e5322d` (`--red`), hover `#c4241f` | See reserved list below |
| Destructive | `#b42318` text on `#fef3f2` with `#fecdca` border (the existing `.form-error` palette) | Remove version, discard extraction, extraction failed message |
| Warning (semantic, shared with the Phase 4 amber status) | text `#93370d` on `#fffaeb`, border `#fedf89` | Low-confidence field highlight, unknown skill badge. Never used for decoration |
| Success (semantic, existing) | text `#067647` on `#ecfdf3`, border `#abefc6` (existing emerald-50/700 family in VaultManager status line) | "Confirmed" badge, diff added lines, status line |

Accent reserved for (explicit, nothing else):
1. The single primary CTA of the current step: "Confirm profile" (review panel) or "Compare versions" (when two are selected)
2. Focus ring (`:focus-visible` 2px `--red`, already global) and field focus border
3. The `aria-pressed` active state of the version filter chips (Base / Tailored / All), matching `.chip[aria-pressed="true"]`
4. Text-link hover color on row actions (existing `hover:text-red-600` pattern)

Not accent: low-confidence, unknown skill, diff lines, badges, "Edited" markers. Those use Warning, Success, Destructive or neutral as defined.

Color is never the only signal (WCAG 1.4.1): every colored state also carries text or a glyph (see State Contract and Diff View).

Contrast checks required at implementation: Warning text `#93370d` on `#fffaeb` >= 4.5:1; Success `#067647` on `#ecfdf3` >= 4.5:1; Destructive `#b42318` on `#fef3f2` >= 4.5:1; `--slate` on `--paper` >= 4.5:1 (passes today).

| State | Visual | Behavior |
|-------|--------|----------|
| Idle | Existing section unchanged. Secondary button "Extract profile" appears beside "Upload file" once there is text (uploaded or pasted >= 200 characters) | Chunk preview continues to work exactly as today |
| Extracting | Inline status block under the buttons: a 16px spinner (CSS rotate, respects reduced motion by becoming static) + text "Reading your resume and building a profile…". Below it, a skeleton of the Profile Review panel (5 grey `--mist` bars, no shimmer under reduced motion). Upload and Extract buttons disabled; textarea `readOnly` | `role="status"`, `aria-live="polite"` on the status text; the panel container gets `aria-busy="true"`. | Success | Status text replaced by "Profile ready to review. {N} fields need a look." (Success color text). ## Surface 2: Profile Review Panel (DOC-01, DOC-02)

### Structure

One panel (`section`, `aria-labelledby` the heading). Header strip (`--mist`) contains the Heading "Review your profile" and a one-line summary: "{N} fields need a look · {M} confirmed of {T}" (counts update live; `aria-live="polite"`).

Groups in fixed order, each an `h3` (group titles use the Body size at weight 600, 15/600) with a `fieldset`/`legend` for form semantics:

1. **Contact**: Name, Email, Phone, Location, Links (one input per link; "Add link" row action)
2. **Roles**: repeating card per role. Fields: Title, Company, Start (month + year), End (month + year, or checkbox "Current role" which disables End), Location (optional), Bullets (a textarea, one bullet per line)
3. **Education**: repeating card. Fields: Degree, Institution, Start year, End year, Detail (optional)
4. **Skills**: the `SkillEditor` (below)
5. **Projects**: repeating card. Fields: Name, Description, Link (optional), Skills used (reuses the SkillEditor chips, read from the project)

Each repeating card has a card-level "Remove {role|school|project}" text button (Destructive color on hover only, plus confirmation, see Copywriting) and an "Add a role / school / project" secondary button below the group.

Layout: field grid is `grid gap-4 sm:grid-cols-2`; long fields (Bullets, Description, Detail, Links) span both columns. Date pairs sit side by side even at 375px in a 2-column sub-grid (month select 55%, year input 45%).

### Validation (typed, validated)

- Dates: month 1-12 or month name via select, year 4 digits between 1950 and current year + 1. Start must not be after End: inline error "End date is before the start date." linked via `aria-describedby`, `aria-invalid="true"`.
- Email: standard format check on blur. Phone: permissive (digits, spaces, +, -, parentheses), no format enforcement beyond at least 7 digits.
- Required to confirm: at least Name. Everything else may be blank (users with no education must not be blocked).
- Validation errors show on blur and on confirm attempt; on confirm attempt with errors, focus moves to the first invalid field and an `role="alert"` summary line reads "Fix {n} field(s) before confirming."

### Per-field state contract

Every field in the panel is one of the following. State is shown as a left marker + badge + border; it is stored in component state keyed by field path.

| State | Trigger | Visual | Text/ARIA |
|-------|---------|--------|-----------|
| Extracted, high confidence | Extractor confidence >= 0.8 (threshold is a constant, assumption 4) | Normal `.field-control`. No badge | None |
| Low confidence | Confidence < 0.8, or value could not be found | Field wrapper `data-confidence="low"`: 3px left bar in Warning border color, input border `#fedf89`, Warning badge "Check this" at the end of the label row (13/600) | Badge text is real text (not only color). Input `aria-describedby` points to a visually hidden "Low confidence: please verify" plus the field's own help id. DOM and tab order are never changed by confidence. A "Next field to check" secondary button in the header strip moves focus to the next low-confidence field. |
| Edited | User changed the value from the extracted value | Badge "Edited" (neutral, `--mist` bg, `--slate` text); low-confidence styling is removed because the user has now vouched for it | "Edited" is appended to the label via visually hidden text |
| Confirmed | User clicked the field's check button, or used "Confirm all" | Badge "Confirmed" (Success). Input stays editable; editing a confirmed field returns it to Edited | Check button is a toggle with `aria-pressed`; accessible name "Confirm {field label}" / "Confirmed, undo" |
| Invalid | Failed validation | Destructive border `#fecdca`, error text under field in Destructive color (13/400) | `aria-invalid`, `aria-describedby` to error id |
| Empty, not found | Extractor returned nothing | Treated as low confidence with placeholder "Not found. Add it or leave blank." | Same as low confidence |

Rules:
- Confirmation granularity is per field (success criterion: "confirm or correct each field") with a per-card and panel-level "Confirm all high-confidence fields" shortcut. "Confirm all" never confirms Low confidence, Invalid or Empty fields.
- A field can be both Edited and Confirmed only in the sense that confirming after editing shows "Confirmed" (Confirmed wins visually; Edited is implicit).
- Per-field confirm control: 44x44px icon button (checkmark glyph) at the right of each input on >= 520px; on < 520px it moves below the input as a text button "Confirm" (44px high, full-width of the field's row end) to preserve input width.

### Panel actions (sticky footer)

- Primary (accent): **"Confirm profile"**. Enabled when Name is present and no field is Invalid. Confirming does the following (UI-visible contract): saves the structured profile, saves the resume chunks (same as today's "Save to vault"), creates the base version entry, and shows Success status "Profile confirmed and saved to your vault." The existing replace-confirmation (`window.confirm`) for an existing resume remains.
- Secondary: "Confirm all high-confidence fields", "Discard" (Destructive text on hover; confirms: see Copywriting).
- Footer is `position: sticky; bottom: 0` on the panel, `--paper` background with a top `--rule` border, 16px padding, safe-area inset padding at the bottom on mobile (`env(safe-area-inset-bottom)`).
- Unconfirmed leave: if the user starts a new upload while edits exist, show the Discard confirmation first.

### Skill Editor (DOC-02)

Skills render as a wrapped list of `.skill-chip` items. Each chip shows the **canonical taxonomy name** as its main label. When the original resume text differed from canonical, the original appears as secondary text.

| Chip variant | Visual | Text |
|--------------|--------|------|
| Canonical, same text | Neutral chip (`--mist` bg, `--rule` border, `--ink` text) | "JavaScript" |
| Normalized from alias | Same neutral chip with a second line/segment in `--slate` 13/400: "from JS" | Chip reads "JavaScript" then "from JS". Screen reader name: "JavaScript, normalized from JS" |
| Unknown (not in taxonomy) | Warning chip (dashed Warning border, `#fffaeb` bg), with badge text "Not in taxonomy" shown on the chip at >= 520px and as a "?" glyph + hidden text below that. Keeps the original text as the label | Screen reader: "{text}, not in taxonomy, kept as written". Clicking opens the chip menu |
| Edited/added by user | Neutral chip with no extra marker; "Edited" appears only in the chip menu | n/a |
| Removed (pending undo) | Chip collapses; a polite status line "Removed {name}. Undo" with a 44px Undo button, available until next edit | `aria-live="polite"` |

Chip menu (popover on click/Enter/Space, `role="dialog"` non-modal or a simple inline expandable row, NOT a hover tooltip): shows the canonical name, aliases the extractor matched, and actions: "Rename" (type a replacement, which re-runs normalization), "Keep as written" (for unknown skills, confirms it as a custom skill, removing the warning), "Remove". Esc closes and returns focus to the chip.

Add skill: a text input "Add a skill" with an inline suggestion list (`role="listbox"` combobox pattern, arrow keys, Enter to pick) drawn from the taxonomy. Typing "js" shows "JavaScript" as the first suggestion with "matched from JS" hint. Enter on free text with no match adds an Unknown chip. Duplicates (two aliases resolving to one canonical) collapse into one chip; the chip then shows "from JS, ReactJS" style aliases joined with commas (max 2 shown, then "+N").

Group skills by category only if the taxonomy supplies one; otherwise a flat list. Default: flat list, sorted by order found in the resume (assumption 6).

Count line under the list: "{N} skills · {K} not in taxonomy" (K omitted when 0).

### Saved-profile entry point

After a profile is confirmed, the existing "Profile" section gains a secondary button "Review structured profile" that reopens the panel pre-filled from the stored profile (no confidence markers since all fields were confirmed; fields show Confirmed). The existing five-field quick profile form stays so current tools keep working; the structured Name/Headline/Location/Links values stay in sync (the structured Contact fields are the source of truth; editing the quick form's Name updates the structured Name).

## Surface 3: Resume Versions (DOC-04)

New section, heading "Resume versions" (Heading role), placed after "Semantic search". Always rendered (it shows its empty state when there are no versions), except it is hidden while `loaded` is false.

### List

- Filter chips (reuse `.chip`, `aria-pressed`): All, Base, Tailored. Each shows a count like `.chip-count`. Default All.
- Sort: newest first. No sort controls.
- Row (`VersionRow`, `li` in a `divide-y rounded-xl border` list like the vault chunk list):

| Element | Spec |
|---------|------|
| Title | Version label, Body 15/600 (e.g. "Base resume" or "Tailored: Senior Backend Engineer, Acme"). Truncates with ellipsis on one line, full text on wrap at < 520px (see mobile) |
| Type badge | "Base" or "Tailored" as text-only neutral badges (no glyph, no colour difference), so colour carries no meaning |
| Targeted job | For tailored: "Targeted: {job title} at {company}" in `--slate` 13/400, with the job link opening in a new tab (`rel="noopener noreferrer"`, text "View posting") when a URL exists. If the job data is missing: "Targeted job not recorded". Base resumes show "Your base resume" |
| Date | Created date as "12 Oct 2026" in `--faint`-safe `--slate` 13/400 (use `<time dateTime>`). `--faint` fails contrast for text; do not use it for this |
| Origin | Optional small text "Created by the application workflow" for entries created by Phase 4. If origin is unknown, omit |
| Actions | "View text" (secondary text button), "Select to compare" checkbox, "Delete version" (Destructive on hover, with confirmation). 44px targets |

- "View" expands the row inline to show the resume text in a bordered `--mist` block (`white-space: pre-wrap`, max-height 320px, scroll). Only one row expanded at a time. Expanded state uses a disclosure button with `aria-expanded` and `aria-controls`.
- The base version can be deleted at any time, with confirmation. Tailored versions keep their own text and are not affected (assumption 8).

### Compare selection

- Each row has a checkbox "Compare" (label visible text "Compare", 44px hit area). Max 2 selected; selecting a third disables the remaining unchecked boxes and shows help text "You can compare two versions at a time."
- A compare bar appears above the list once >= 1 is selected: "{n} of 2 selected" + primary (accent) button **"Compare versions"** (disabled until exactly 2; `aria-disabled` with explanation text "Select one more version") + "Clear selection".
- Fallback for users who prefer not to use checkboxes (and for 375px): two `select` controls, "From" and "To" (labels visible), listing all versions, sit inside the compare bar and stay in sync with the checkboxes. (This is the accessible, mobile-friendly path.) Order rule: older version is "From" by default; the user may swap with a "Swap" secondary button.
- Quick action: on a tailored row, a text button "Compare with base" preselects that version and the most recent base version.

### Empty list state

Uses `.empty` styling (dashed border, centered, 32px/24px padding).

- Heading: "No resume versions yet"
- Body: "Confirm your profile above to save your base resume. Tailored versions show up here, with the job each one targeted."
- Action: if an extraction is waiting, link-button "Review your profile"; otherwise none.

Single-version state (one base, nothing tailored): list shows the row; compare bar is hidden; a quiet line under the list reads "Tailor your resume to a job and the new version will appear here so you can compare." No fake rows.

### Diff view (`VersionDiff`)

Opens below the compare bar, replacing nothing (list stays above). Container: bordered panel with header strip: "Comparing {From label} → {To label}" (diff header title: Body 15/600) and counts "{a} added · {r} removed · {c} changed" and a "Close diff" secondary button (focus returns to the Compare versions button).

Unit of comparison: lines of the plain-text rendering of each resume (the same text the vault stores; sections like "EXPERIENCE" are just lines). Algorithm detail is the planner's choice, but the visual contract is:

| Line type | Visual | Non-color signal |
|-----------|--------|------------------|
| Added | Success bg `#ecfdf3`, 3px left bar `#067647` | Gutter glyph "+" and visually hidden prefix "Added: " |
| Removed | Destructive bg `#fef3f2`, 3px left bar `#b42318` | Gutter glyph "−" (U+2212) and hidden prefix "Removed: " |
| Changed | Rendered as a removed line immediately followed by an added line (a pair), with word-level emphasis inside both: changed words get a stronger background (`#abefc6` on added, `#fecdca` on removed) plus `font-weight: 600` | Same "+" / "−" gutter; pair is grouped with `role="group"` and `aria-label="Changed line"` |
| Unchanged context | Plain `--paper` background, `--slate` text, blank gutter | n/a |

- Unchanged runs longer than 6 lines collapse to a single full-width button row "Show {n} unchanged lines" (`aria-expanded`), keeping 3 lines of context above and below each change.
- Layout: unified (single column) at all widths. Line numbers are not shown (resumes are prose, and this saves width). Gutter is a fixed 24px column. Lines wrap (`white-space: pre-wrap; overflow-wrap: anywhere`); no horizontal scroll.
- Navigation: "Previous change" / "Next change" secondary buttons (44px) in the header; they move focus to the change group and scroll into view. Keyboard shortcuts are not required.
- Summary for screen readers: the header counts live in an element with `role="status"` that is announced once on open.
- States of the diff:
  - Identical texts: replace the body with the line "These two versions are identical." plus the counts all 0. No empty diff box.
  - One side has no text (corrupt entry): `.form-error` "One of these versions has no text to compare."
  - Very large (> 2,000 lines): compute in a `requestAnimationFrame`/worker-free chunk, show "Comparing…" status; if it exceeds 1 s, still render collapsed unchanged runs only. (Resumes rarely exceed 300 lines; this is a guard.)
  - Same version selected twice: prevented. Both selects exclude the other's current value, and "Compare versions" stays disabled.

## Responsive: 375px (mobile) contract

Breakpoints reuse the project's existing ones: 520px (compact), 760px.

At 375px (content width 335px after `px-5`):

- Page column: single column, `px-5`. No horizontal page scroll anywhere in the new UI (verify at 375 and 320).
- Profile Review field grid collapses to one column (`sm:` breakpoint, 640px, already the grid switch). Date pairs stay as a 2-column sub-grid.
- Per-field confirm control moves under the input as a text button (see above). The "Check this" / "Edited" / "Confirmed" badge moves to its own line under the label (wraps via `flex-wrap`), never truncating label text.
- Role/Education/Project cards: full-width, `p-4` (16px) instead of 24px; card actions ("Remove") become a full-width secondary button at the bottom of the card.
- Sticky footer: "Confirm profile" is full-width (min-height 48px). Secondary actions ("Confirm all high-confidence fields", "Discard") move into a row above it, each full-width, stacked, or into a single "More" disclosure if three items would take more than 25% of viewport height. Footer must not cover the focused input: set `scroll-padding-bottom` on the panel equal to the footer height.
- Skill chips wrap; "Not in taxonomy" text label is replaced by "?" + hidden text; the chip menu opens as an inline expanding block under the chip row (not a floating popover) to avoid viewport overflow.
- Version rows: stack vertically. Title wraps to two lines max, then ellipsis. Metadata lines (targeted job, date) go on separate lines. Actions form a row of 44px text buttons; "Compare" checkbox row spans full width at the top of the action row.
- Compare bar: "From"/"To" selects stack, each full width; "Compare versions" is full-width (48px). Checkbox selection remains available.
- Diff: unified layout; gutter 24px; body text 15px with wrapping; header counts wrap to 2 lines; "Previous/Next change" buttons sit side by side at 50% width each.
- Minimum body size 15px (no pinch-zoom required). Inputs are 16px effective on iOS to avoid zoom: `field-control` font-size is 14.5px today, which triggers iOS Safari zoom on focus. New fields under 520px set `font-size: 16px` (this is a phase-local override, noted as an exception to the 15px Body size).
- Landscape/zoom 200% and text-spacing overrides must not clip content: no fixed heights on rows or cards.

## Accessibility Contract (WCAG 2.2 AA)

- Landmarks and headings: new panel and section are `section[aria-labelledby]`. Heading order h2 (panel/section) then h3 (groups). No skipped levels.
- Labels: every input has a visible `<label htmlFor>`. Repeating cards give each field a unique accessible name by including the card context via `aria-labelledby` with two ids (card title + label), e.g. "Role 2 Company".
- Focus: global `:focus-visible` red 2px outline is retained. Focus is never lost on state changes: after Confirm profile success, focus moves to the success status heading; after Remove card, focus moves to the previous card's Remove/heading (or the group's Add button if none); after Close diff, focus returns to "Compare versions".
- Keyboard: all functions reachable by Tab/Shift+Tab, Enter and Space. Skill combobox uses arrow keys, Enter, Esc. Chip menu closes on Esc. No keyboard traps.
- Live regions: one polite `role="status"` region for extraction progress, summary counts, and undo messages; one `role="alert"` for extraction failure and validation summary. Do not announce every keystroke.
- Status is never color alone: Low confidence = "Check this" text; Edited/Confirmed = text; diff = "+"/"−" glyphs and hidden prefixes; unknown skill = text/"?" with hidden text.
- Contrast: text >= 4.5:1; UI component borders (input borders, chip borders) >= 3:1 against adjacent colors where they are the only affordance. The existing `#d5d8de` field border is 1.5:1 and is treated as an inherited weakness; the new focus and invalid states exceed 3:1. Do not use `--faint` (`#8c919c`) for text in new UI.
- Targets: >= 44x44 CSS px for all interactive controls (see Spacing).
- Motion: spinner and skeleton shimmer disabled under `prefers-reduced-motion` (the global rule already shortens animations to ~0; spinners must also render as a static glyph with the text status).
- Forms: `autocomplete` attributes on Contact fields (`name`, `email`, `tel`, `address-level2` or `off` for the free-text location; links `url`). Errors are associated via `aria-describedby` and are announced on blur and on confirm.
- Zoom/reflow: usable at 400% zoom / 320px width without two-dimensional scrolling (see Responsive).
- Diff semantics: render as a `ul` of `li`s (not a table), each prefixed with visually hidden "Added:" / "Removed:" / "Unchanged:" only for changed lines (unchanged lines are not prefixed to reduce noise; collapsed runs are announced by the button label).
- Checkbox group for compare selection is a `fieldset` with legend "Choose two versions to compare".

## Interaction Flow Summary

1. Upload file (or paste) on `/vault` -> text is parsed (existing `/api/parse-document`) -> chunk preview updates (existing) -> extraction starts automatically for uploads (explicit button for pasted text).
2. Extracting -> Success: Profile Review panel with markers. Failure: error block, chunk-only flow intact.
3. User edits/confirms fields and skills -> Confirm profile -> chunks saved, profile saved, base version created -> Success status; panel collapses to a summary row with "Review structured profile".
4. Versions section lists base (and later tailored) versions. Select two -> Compare versions -> Diff view -> Close diff.

## Assumptions for the user to confirm

No CONTEXT.md and no live user. Each item below is a decision made by default.

1. **Placement**: everything on `/vault`, no new route, with the review panel inline under "Add your resume". Alternative: a modal/stepper. Chosen for consistency with the single-page vault and accessibility simplicity.
2. **No shadcn / no icon library**: matches current codebase; inline SVG for icons.
3. **Typography**: 15 / 13 / 20 sizes, weights 400 and 600 only, deviating from existing 12.5/13.5/14.5/650/700/800 usage in new code. Existing sections are not retrofitted.
4. **Low-confidence threshold**: 0.8 on a 0-1 confidence returned per field by the extractor. If the extractor (Phase 5 plans) gives no per-field confidence, the fallback is "missing, malformed, or failed validation = low confidence". The planner must expose a confidence value or boolean per field in the profile type.
5. **New Warning color** (amber) introduced for low-confidence and unknown skills, because red is reserved for the brand accent and destructive actions and green for success.
6. **Skills list is flat**, ordered as found in the resume, with no category grouping, unless the taxonomy already carries categories.
7. **Removing a role/school/project**: inline Undo status instead of a modal if cheap; otherwise `window.confirm` like the rest of the vault.
8. **Version removal always allowed** (with confirmation), even for the base. Tailored versions are self-contained text and are not invalidated.
9. **ResumeField on tool pages** is left unchanged (no extraction there). Optional one-line help-text pointer only.
10. **Diff granularity is line-based** with word-level emphasis inside changed pairs, **unified layout only** (no side-by-side), and no export of diffs.
11. **Compare model**: exactly two versions, via checkboxes plus From/To selects; no three-way compare, no restore/"make this the base" action in this phase (not in the requirements).
12. **Confirm profile also saves resume chunks and creates the base version**, so one action finishes the flow. If the team prefers separate "Save profile" and "Save to vault" actions, the panel footer needs a second button.
13. **Quick profile form stays** and shares Name/Location/Links with the structured Contact section, to avoid breaking tools that read `VaultProfile`.
14. **Job reference on tailored versions**: assumed to carry job title, company and optional URL from Phase 4. If Phase 4 stores only free text, the row shows that text under "Targeted:".
15. **Mobile form font-size**: 16px for new inputs under 520px (iOS zoom prevention), a deliberate exception to the 15px Body size.
16. **Skill unknown handling**: unknown skills are kept as written and flagged, never dropped or auto-guessed.
